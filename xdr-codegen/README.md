# xdrc

`xdrc` compiles an XDR specification (a `.x` file) to a Rust module. It
replaces the Rust backend of x23c, the C++ compiler in hogd's `x23/x23c`,
and accepts the same dialect and the same options as `x23c --rust`. Its
output has the same public API as x23c's, with tidier code.

The crate is `thruput-xdr-codegen` (library `xdr_codegen`). It is not
published. Why xdrc exists and how it is built are in [DESIGN.md](DESIGN.md);
deferred work is in [TODO.md](TODO.md).

## Installing

From a checkout of this repository:

```shell
cargo install --path xdr-codegen --bin xdrc
```

Or pinned to a commit, without a checkout:

```shell
cargo install --locked --git https://github.com/thruputchain/xdrs \
  --rev COMMIT --bin xdrc thruput-xdr-codegen
```

## Running

```text
xdrc [OPTIONS] [-o FILE] file.x
  --help                      print usage and exit
  --version                   print version and exit
  --strict                    fail if there are any warnings
  --rust                      generate Rust (the default and only output)
  -o FILE                     write to FILE (`-` for standard output);
                              by default, file.rs in the current directory
  --recursive_type TYPE       box TYPE wherever it appears
  --rust-feature FEATURE      treat FEATURE as on, instead of gating on it
  --rust-no-feature FEATURE   treat FEATURE as off, leaving out what it gates
```

- `-oFILE` works as well as `-o FILE`, and `--` ends the options.
- Only one input file is allowed.
- `--rust` does nothing; it is accepted so that `x23c --rust` command
  lines work unchanged.
- The options `--rust-feature`, `--rust-no-feature` and
  `--recursive_type` may be repeated. Naming a feature both on and off is
  an error.
- If writing the output fails, xdrc removes the partial file, so a build
  never takes a truncated file as current.
- Exit status: 0 on success, 1 on any error, including a warning under
  `--strict`.

The output starts with `// Generated by xdrc VERSION. Do not edit.`,
followed by the `.x` file's header comment.

### As a library

`xdr_codegen::parse(src)` returns the syntax tree and its warnings, or all
the diagnostics if there was an error. `xdr_codegen::rust::generate(&spec,
&options)` turns the tree into the text of a Rust module. `xdr_codegen::diag`
formats diagnostics with line and column.

## The dialect

xdrc accepts [RFC 4506] XDR, plus:

- [RFC 5531] `program` definitions, with `version` and procedure
  definitions;
- `namespace NAME { ... }` around definitions, which may nest;
- `%` lines, passed through to x23c's C++ output. xdrc parses and keeps
  them, but the Rust backend ignores them;
- markers in comments, such as `#[rust(newtype)]` (see below).

The full grammar, in EBNF, is in the module docs of `src/parser.rs`.

[RFC 4506]: https://datatracker.ietf.org/doc/html/rfc4506
[RFC 5531]: https://datatracker.ietf.org/doc/html/rfc5531

### Rules beyond the grammar

- A union has at least one arm, and only the last arm can be `default`.
- A struct has at least one field, which may be `void`.
- Every arm of a union has at least one `case` or `default` label.
- Type names must be unique across the file, namespaces included.
  Duplicate `const` names are allowed, as in x23c.

### Lexing

The tokens are those of x23c's flex scanner, which gives some unusual
results:

- The longest match wins, so `constant` is an identifier, not the keyword
  `const` followed by `ant`.
- `char`, `short`, `inline` and `sizeof` are reserved, and using one is an
  error.
- A number matches `[+-]?([0-9'_]+|0x[0-9a-fA-F'_]+)`. So `'` alone, or
  `_1'`, lexes as a number, which is then rejected as invalid.

### Numbers

- `'` and `_` are separators and are ignored.
- `0x` makes a number hexadecimal, and a leading `0` makes it octal, as in
  RFC 4506 and C++. `08` is an error.
- A number must fit an `i64` or a `u64`.

In the output, `'` becomes `_`, and an octal number becomes `0o...`
(Rust would read `010` as ten).

### Comments

Comments become documentation in the output, and carry the markers, so
xdrc keeps them and attaches each to a definition. Every token can have a
*leading* and a *trailing* comment:

- **A leading comment** is one or more whole lines, each holding only a
  comment. It attaches to the next token. If a blank line separates it
  from that token, the comment keeps a trailing blank line.
- **A trailing comment** is any other comment, and attaches to the token
  before it.
  - A trailing `//` comment continues onto the lines below it that start
    with `//`, but not `///` or an empty `//`.
  - A comment that shares its line with later code, as in
    `/* x */ int b;`, is a trailing comment of the token *before* it, so it
    documents the previous field, not `b`.
- **The header:** before the first definition, comment blocks that a blank
  line sets off from what follows form the file's header, typically a
  license notice. The last such block leads the first definition instead.
- Comments after the last definition are dropped.

Each kind of definition takes its comment from particular tokens:

| Definition | Comment |
|---|---|
| `typedef`, `const` | The leading comment of the keyword, then the trailing comment of the `;`. So `typedef T X; // #[rust(newtype)]` gets its marker. |
| `enum`, `struct`, `union` | The leading comment of the keyword. A comment after the closing `};` is dropped. |
| Struct field, union arm | The leading comment of the declaration, then the trailing comment of its `;` |
| Enum member | The leading comment of its name, then the trailing comments of its value and of the following `,` |
| Procedure | The leading comment of its result type, then the trailing comment of its `;` |
| `program`, `namespace` | The leading comment of the keyword |

Comments before a `case` label, and on `version` definitions, are dropped.

In the output:

- `///` comments and `/** */` comments are doc comments.
- `//` and `/* */` comments stay plain `//` comments.
- Each line is kept, including empty lines that separate paragraphs, but
  not empty lines at the start or end of a `/* */` comment.

### Markers

Markers go anywhere in a definition's comment. xdrc removes them from the
output, along with any comment line that held only markers.

| Marker | Where | Effect |
|---|---|---|
| `#[rust(newtype)]` | typedef | A transparent struct wrapping the type, rather than an alias |
| `#[rust(box_ptr)]` | field or arm | Box the element type |
| `#[rust(const=u64)]` | const | Type `u64` |
| `#[rust(const=u32)]` | const | Type `u32`, the default |
| `#[rust(ConstWriteXDR)]` | enum, struct, union | Also derive `ConstWriteXDR` |
| `#[rust(no_debug)]` | enum, struct, union, newtype | Leave out `Debug`. Inline types defined within do not inherit this. |
| `#[rust(no_eq)]` | enum, struct, union, newtype | Derive only `Clone`, `Debug`, `PartialEq` and `PartialOrd` |
| `#[doc(hidden)]` | anywhere | Emit `#[doc(hidden)]` after the comment |

`--recursive_type T` boxes `T` everywhere, as `#[rust(box_ptr)]` does for
a single field.

## The generated Rust

The module is written to be included in a crate that provides:

- the features `serde`, `xdrs`, `schema`, `spec` and `std`, each gating
  what it covers with `#[cfg]` or `#[cfg_attr]`;
- through `use crate::*`, anything the specification refers to but does
  not define, such as types from another `.x` file;
- as dependencies, `xdrs` and, for programs, `thruput-rpc-api` and
  `async-trait`.

`--rust-feature F` emits what F covers with no condition, and
`--rust-no-feature F` leaves it out.

| XDR | Rust |
|---|---|
| `const` | `pub const NAME: u32 = VALUE;`, or `u64` with the marker |
| `typedef` | `pub type NAME = TYPE;` |
| `typedef` with `#[rust(newtype)]` | `pub struct NAME { inner: T }` with `From`, `new`, `into_inner`, `Deref` and `DerefMut`. A fixed opaque newtype also gets `AsRef<[u8]>`, hex serde, a hex-string `JsonSchema` and `Copy`. |
| `enum` | An open newtype `pub struct NAME(pub i32)`, with an associated constant per member, `From<i32>`, `XDRDiscriminant` and `Display`. Decoding accepts any `i32`. |
| `struct` | A `#[repr(C)]` struct with `pub` fields |
| `union` | A `#[repr(i32)] #[non_exhaustive]` enum with one variant per case label, and an accessor named after the switch variable that returns the discriminant |
| An inline `struct`, `union` or `enum` | A type named `PARENT_FIELD`, emitted before its parent |
| `program` | For each version `V` of program `P`: a handler trait `P_V`, `P_V_Dispatcher` and `P_V_Client`, against `thruput_rpc_api` |

Some details of unions:

- Variants are named after their case labels: `_5`, `_neg1`, `_0x10`, a
  member name, `TRUE` or `FALSE`, or `_CONST` for a constant.
- Each variant's tag is its case value as an `i32`. An unsigned value
  keeps its bit pattern.
- The default arm becomes a variant whose first field holds the
  discriminant, typed by the switch type, and whose tag is the least `i32`
  that no case uses. When the switch type is an alias, in the same file, of
  `int`, `unsigned int` or `bool`, the field has that primitive type
  instead, which the derived const writers need.

A fixed opaque struct field or union arm serializes as a hex string with
`serde`, and has a matching `schemars` attribute.

## Diagnostics

Diagnostics are printed to standard error as `file:line:col: error: ...`
or `file:line:col: warning: ...`. Columns count characters, with a tab
advancing to the next multiple of 8 plus one.

Every lexical error is reported. Parsing stops at the first syntax error,
and the checks on names and values run only on a file that parses.

Warnings, which `--strict` makes errors:

- a trailing comma in an enum
- `unsigned` without `int` or `hyper`
- `case` labels on the default arm
- lowercase `true` or `false` as a case label, which xdrc treats as `TRUE`
  or `FALSE`
- `int32_t`, `uint32_t`, `int64_t` or `uint64_t` as a type name

Errors that come from generating Rust, where x23c would generate code that
does not compile, or code that is wrong:

- `quadruple`
- a union switched on a type other than `int`, `unsigned int`, `bool` or a
  named type
- a `bool` switch with a case other than `TRUE` or `FALSE`
- a case value outside the switch type's range, for an `int` or `unsigned
  int` switch (directly or through aliases), when the value is a number or
  a constant of the file
- an enum member value that does not fit an `int`, when it is a number or a
  constant of the file
- a negative length
- a name that cannot be a Rust identifier: `self`, `Self`, `super`,
  `crate` or `_`. Other Rust keywords become raw identifiers, such as
  `r#type`.
- a procedure named `new` or `prog_vers`, which would collide with a
  method of the generated client
- two procedures of the same name in one version

## Differences from x23c

xdrc's output has the same public API as x23c's for the same input, but
not the same text. Where x23c accepted input and produced code that did
not compile or was wrong, xdrc either generates working code or reports
an error.

### Input

| | x23c | xdrc |
|---|---|---|
| An invalid octal number such as `08` | Accepted; the C++ fails to compile | Rejected |
| A number that does not fit 64 bits | Accepted, with a wrong value | Rejected |
| `/* x **/` as a trailing comment | Rejected | Accepted |
| A comment after an enum's trailing comma | Dropped | Kept on the last member |
| Comments on `program` and `namespace` | Dropped, and emitted as C++, respectively | Kept on the definition |
| A syntax error at the end of the file | Reported at the last token | Reported at the end of the file |
| Diagnostic text | | Reworded, with `error:` on errors |

Otherwise, xdrc accepts and rejects the same inputs, with errors and
warnings at the same lines and columns.

### Output

Formatting:

- The code is formatted by `prettyplease`, so lines wrap and imports sort
  differently.
- The header is `Generated by xdrc VERSION. Do not edit.` instead of
  x23c's commit hash and its `DO NOT CHECK IN` line.
- Each union's accessor follows the union, rather than sitting under an
  "XDR internals" banner.
- The RPC client's SAFETY note comes before each method rather than inside
  it.
- Array lengths that are numbers drop x23c's `as usize`.

Comments:

- Markers leave no comment lines behind. x23c left `#[rust(box_ptr)]` in
  its output.
- Union variants lose x23c's `// case X:` and `//   TYPE NAME;` lines.
- A struct or union with an inline type keeps its own doc comment. x23c
  gave it to the first inline type instead.

Constructs x23c mishandled, which xdrc generates correctly:

- `typedef struct { ... } T;` defines `T`; x23c emitted `pub type T = T;`.
- An inline type under `*`, `[]` or `<>` is named consistently; x23c
  produced names like `S_Option<...>`.
- `'` in a bound such as `<1'000>` becomes `_`; x23c changed it only in
  constants.
- An enum member whose value is a name: another member of the same enum
  (`Self(Self::A.0)`), a member of another enum in the file
  (`Self(Other::X.0)`), or a constant (`Self(K as i32)`). x23c emitted the
  bare name, which does not compile. A name the file does not define is
  taken for a constant from another file.
- A case label that is a constant of the file, in a union switched on a
  named type, gives variant `_K` with value `K as Switch`. x23c took it for
  an enum member.
- Lowercase `true` and `false` case labels become `TRUE` and `FALSE`. x23c
  crashed on them in a `bool` switch, and elsewhere named the variant
  `_true`.
- A fixed opaque union arm serializes as hex, as a struct field does. x23c
  left it a bare `[u8; N]`, which with `serde` did not compile beyond 32
  bytes and below that serialized as an array of numbers.
- A fixed opaque newtype whose length is a named constant gets a
  `JsonSchema` and no `Default`; x23c threw an exception.
- With `spec` but not `xdrs`, the output compiles: `use xdrs::*` and a
  union's `#[xdr(default_variant)]` are gated on either feature.
- Every Rust keyword, including reserved ones such as `try`, `gen` and
  `box`, becomes a raw identifier. x23c's list was shorter.

## Testing

```shell
cargo test -p thruput-xdr-codegen
cd xdr-codegen/check && cargo test --all-features && cargo test --no-default-features
```

- **Unit tests:** `tests/parse.rs` covers comment attachment,
  declarations, inline types, unions, programs, namespaces, `%` lines,
  numbers, warnings and errors. `tests/rust.rs` covers what the backend
  rejects, raw identifiers, number forms, comments, markers, union case
  names and forced features. `src/rust/comment.rs` tests comment printing.
- **Golden test:** `tests/golden.rs` regenerates `check/src/generated.rs`
  and `check/src/plain.rs` from `check/check.x` and `check/plain.x`, and
  fails if they differ from the committed files. After changing the
  generator, run it with `XDRC_BLESS=1` and review the diff.
- **Check crate:** `check/` (`thruput-xdrc-check`) compiles those modules
  against this workspace's `xdrs` and `thruput-rpc-api` and runs their
  tests. Test it with all features and with none.
- **Corpus test:** `tests/corpus.rs` parses, and generates Rust from, every
  `.x` file under the directories in `XDRC_CORPUS`, separated by `:`. It
  is skipped when `XDRC_CORPUS` is unset:

  ```shell
  XDRC_CORPUS=../thruput-protocol:../hogd/x23/tests \
    cargo test -p thruput-xdr-codegen --test corpus -- --nocapture
  ```

### protocol-rs

thruput-protocol-rs, the main consumer, generates its sources with a
pinned xdrc. Before it switched, its 63 generated files were regenerated
with xdrc in place of x23c (on 2026-11-06), and all of these passed:

- `cargo check --workspace --all-features --all-targets` and
  `cargo test --workspace --all-features`
- every `cargo build` combination in its `scripts/ci-check.sh`, including
  the `riscv32im-unknown-none-elf` builds and the RPC crates
- `ci-check.sh`'s clippy command; workspace-wide clippy with all features
  gives the same 25 warnings as on x23c's output
- a comparison of the public API of all 11 crates, from rustdoc's JSON
  output: every public item, field type, enum variant and discriminant,
  constant value, trait impl and method signature, 21,435 lines, all
  identical
- hogd's `x23/tests/rust_check/check.sh`, run with xdrc

That API comparison is now protocol-rs's `scripts/compare-xdrc-api.sh`.
Run it there before moving protocol-rs to a newer xdrc, or after changing
the backend:

```shell
scripts/compare-xdrc-api.sh --xdrc PATH/TO/xdrc
```

It generates protocol-rs's sources with x23c and with xdrc, and diffs a
summary of each crate's public API. By default it uses the latest x23c
release and the pinned xdrc; `--x23c` and `--xdrc` select other builds,
and `--keep` keeps the work directory. `--docs` and `--attrs` also compare
doc comments and attributes. With `--attrs` the summaries are identical;
with `--docs` they differ only in the `AuthClaim` doc comment, which x23c
gives to an inline type (see "Differences from x23c").

The fixtures `check/check.x` and `check/plain.x`, and the tests in
`check/src/lib.rs`, are adapted from hogd's `x23/tests/rust_check`, which
is under the GPL-3 like the rest of hogd's `x23` tree, while this
repository is Apache-2.0.
